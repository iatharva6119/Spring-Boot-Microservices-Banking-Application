# 🏦 Spring Boot Microservices Banking Application

A highly scalable, production-ready backend banking application built using **Java 17, Spring Boot, Spring Cloud**, and deployed on **Kubernetes** with an **Istio Service Mesh**. 

This project demonstrates a robust microservices architecture where banking responsibilities are divided into independent services. It features advanced cloud-native patterns including **Distributed Tracing (Jaeger), Centralized Logging (Loki + Fluent Bit), Service Topology visualization (Kiali)**, and deep performance monitoring via **Prometheus & Grafana**.

## 📖 Project Overview

This project mimics a real-world digital banking backend. It moves away from monolithic design by separating core banking operations into highly decoupled microservices. 

Business capabilities include:
- **User onboarding:** Secure registration, profiling, and Identity Management via Keycloak.
- **Account operations:** Bank account creation, sequential account number generation, and balance inquiries.
- **Transactions:** Deposits, withdrawals, and exhaustive transaction histories.
- **Fund Transfers:** ACID-compliant internal fund transfers between multiple accounts.

---

## 🚀 Key Features Implemented

1. **Microservices Architecture:** 7 separate components managing different bounded contexts of the banking domain.
2. **Database-per-Service Pattern:** Each microservice manages its own isolated MySQL database, ensuring loose coupling.
3. **Synchronous Inter-Service Communication:** Handled via **OpenFeign** integrated with **Netflix Eureka** for dynamic service discovery.
4. **API Gateway & OAuth2:** Centralized ingress routing via Spring Cloud Gateway, which acts as an OAuth2 Resource Server validating JWTs generated by Keycloak.
5. **Container Orchestration:** Fully containerized using Docker, with YAML manifests for deployment onto **Kubernetes (K8s)**.
6. **Istio Service Mesh:** Deployed with Istio to manage traffic, enforce mutual TLS (mTLS) for zero-trust security, and provide fault injection capabilities.
7. **Comprehensive Observability Suite:**
   - **Metrics:** Prometheus & Grafana & Kube-State-Metrics.
   - **Tracing:** Jaeger for distributed transaction tracking.
   - **Logging:** Loki and Fluent Bit for unified log querying.
   - **Topology:** Kiali for real-time visualization of service dependencies and traffic flows.

## 🧩 Microservices Architecture

Here is a detailed breakdown of each service in the application ecosystem:

### 1. API Gateway (Port 8080)
The unified front door for the application. Uses **Spring Cloud Gateway**.
- Routes external requests to the appropriate backend microservices based on URL paths (`/api/users/**`, `/accounts/**`, etc.).
- Integrates with Keycloak to validate JWTs before forwarding requests.

### 2. Service Registry - Eureka (Port 8761)
The application's dynamic address book.
- Microservices register themselves here on startup.
- Allows services to communicate using logical names (e.g., `lb://account-service`) rather than hardcoded IP addresses.

### 3. User Service (Port 8082)
Manages user profiles and identities.
- Exposes APIs for user registration.
- Communicates directly with the **Keycloak Admin API** to provision IAM (Identity and Access Management) credentials when a user registers.

### 4. Account Service (Port 8081)
Manages bank account lifecycles.
- Validates user existence (via Feign call to User Service).
- Fetches unique account numbers from the Sequence Generator.
- Manages account balances, status updates (ACTIVE, BLOCKED, CLOSED), and retrieves transactions.

### 5. Sequence Generator (Port 8083)
A highly specialized microservice whose sole job is to generate strictly sequential numbers.
- Ensures no two bank accounts ever receive the same account number.

### 6. Transaction Service (Port 8084)
The system of record for all monetary movements.
- Processes deposits and withdrawals.
- Calculates balance deltas and calls the Account Service to update the ledger.

### 7. Fund Transfer Service (Port 8085)
Orchestrates complex, multi-leg internal transfers.
- Validates sufficient balances and account statuses for both the sender and receiver.
- Performs a 2-phase commit style orchestration by debiting one account, crediting another, and logging the transactions via the Transaction Service.

## 🔭 Advanced Cloud-Native Features Explained

### 1. Istio Service Mesh
In a standard microservice architecture, managing network logic (retries, timeouts, security) within the application code is cumbersome. This project uses **Istio** to offload these concerns to the infrastructure layer.

**How it works:**
- **Sidecar Proxy (Envoy):** Istio injects a lightweight Envoy proxy container alongside every microservice pod. All incoming and outgoing traffic passes through this proxy.
- **mTLS (Mutual TLS):** The Envoy proxies automatically encrypt traffic between microservices. Even if the internal network is compromised, the traffic remains secure.
- **Traffic Management & Resilience:** Istio handles Ingress routing (via `istio-ingress.yaml`), and can perform fault injection (e.g., artificially delaying responses to test system resilience) using `VirtualService` resources.

### 2. Distributed Tracing (Jaeger)
When a user executes a "Fund Transfer", the request touches the Gateway, Fund Transfer Service, Account Service, and Transaction Service. If the request is slow or fails, finding the bottleneck is nearly impossible without tracing.

**How it works:**
- Istio Envoy sidecars automatically generate and propagate **Trace Headers** (like `x-b3-traceid`).
- These spans are asynchronously shipped to the **Jaeger backend**.
- Using the Jaeger UI, you can search for a single HTTP request and see a visual waterfall chart of exactly how long it spent in the Gateway, how long the database query took, and which specific microservice threw an error.

### 3. Centralized Logging (Loki + Fluent Bit)
Checking logs by SSHing into individual pods or running `kubectl logs` across 7 different services is inefficient.

**How it works:**
- **Fluent Bit** is deployed as a DaemonSet to every Kubernetes node. It automatically tails the raw container logs located at `/var/log/containers/*.log`.
- It parses these logs, adds Kubernetes metadata (pod name, namespace, labels), and forwards them to **Loki**.
- **Loki** indexes the log streams (similar to Prometheus for metrics).
- You can open **Grafana**, select Loki as a data source, and query logs across the entire cluster using LogQL (e.g., `{app="fund-transfer-service"} |= "Exception"`).

## 💻 Getting Started (Commands)

### Prerequisites
- Docker & Docker Compose
- Minikube or a local Kubernetes cluster (e.g., Docker Desktop K8s, Kind)
- `kubectl` CLI installed
- `istioctl` installed (v1.23.0+)

### Deploying to Kubernetes (with Istio)

1. **Start your Kubernetes Cluster**
2. **Install Istio & Label the Namespace:**
   ```bash
   istioctl install --set profile=default -y
   kubectl create namespace banking
   kubectl label namespace banking istio-injection=enabled
   ```
3. **Deploy the Architecture:**
   Navigate to the repository root and apply the Kubernetes manifests:
   ```bash
   # Deploy databases and secrets
   kubectl apply -f k8s/banking-secret.yaml -n banking
   kubectl apply -f k8s/banking-configmap.yaml -n banking

   # Deploy the microservices
   kubectl apply -f k8s/eureka/ -n banking
   kubectl apply -f k8s/api-gateway/ -n banking
   kubectl apply -f k8s/user-service/ -n banking
   kubectl apply -f k8s/account-service/ -n banking
   kubectl apply -f k8s/sequence-generator/ -n banking
   kubectl apply -f k8s/transaction-service/ -n banking
   kubectl apply -f k8s/fund-transfer/ -n banking

   # Apply Istio Traffic Management & Ingress
   kubectl apply -f k8s/istio-ingress.yaml -n banking
   kubectl apply -f k8s/istio-mtls.yaml -n banking
   ```

4. **Deploy the Observability Stack:**
   ```bash
   kubectl apply -f k8s/monitoring/ -n banking
   ```

### Running locally via Docker Compose (Alternative)
If you do not want to use Kubernetes, you can run the basic Docker Compose stack (Note: This does not include Istio/Jaeger/Loki).
```bash
# Build all images and start containers
docker-compose up --build -d
```

### Accessing Observability Dashboards (Kubernetes)

Use port-forwarding to access the telemetry UIs securely from your local machine:

- **Kiali (Service Topology):**
  ```bash
  kubectl port-forward svc/kiali 20001:20001 -n banking
  # Visit: http://localhost:20001
  ```
- **Jaeger (Distributed Tracing):**
  ```bash
  kubectl port-forward svc/jaeger-query 16686:16686 -n banking
  # Visit: http://localhost:16686
  ```
- **Grafana (Metrics & Logs):**
  ```bash
  kubectl port-forward svc/grafana 3000:3000 -n banking
  # Visit: http://localhost:3000
  ```
- **Prometheus (Raw Metrics):**
  ```bash
  kubectl port-forward svc/prometheus 9090:9090 -n banking
  # Visit: http://localhost:9090
  ```

## 🗄️ Database Architecture
The application adheres strictly to the database-per-service pattern. Data is isolated to prevent tight coupling.
- `user_service_db`: Tables for `user` and `user_profile`.
- `account_service_db`: Tables for `account`.
- `sequence_generator_db`: Table for `sequence`.
- `transaction_service_db`: Table for `transaction`.
- `fund_transfer_service_db`: Table for `fund_transfer`.

## 🔐 Security Model
1. **Edge Security:** The Istio Ingress Gateway manages all incoming traffic.
2. **Authentication:** The client authenticates against Keycloak (`:8571`) to receive an OAuth2 Bearer Token (JWT).
3. **Authorization:** The API Gateway intercepts requests, validates the JWT signature against Keycloak's public keys, and enforces role-based access before routing.
4. **Internal Security:** Istio enforces strict mTLS between all pods, ensuring that internal East-West traffic cannot be sniffed.
